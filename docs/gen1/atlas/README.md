# The Gen 1 memory atlas

[← Gen 1 area](../README.md) · **[by address](by-address.md)** · **[by name](by-name.md)** · **[the structures](structures.md)**

**Every address in Pokémon Red and Blue, what lives there, and — for most of them —
evidence that we watched the cartridge use it.**

The [memory map](../memory-map.md) beside this page is *task-shaped*: it covers the party, the
battle, the screen, the map and the dice, because those are what this project's plugins needed.
This is the other thing. It is a walk of the **whole address space**, region by region, and it
says what is unused as carefully as it says what is used.

---

## Why build another one

Memory maps for these games already exist. The disassembly has `ram/wram.asm`; the wikis have
tables; the cheat-code sites have lists. **They are transcriptions.** Somebody read an address
once and everybody since has copied it, and there is no way, from inside any of them, to tell a
right address from a plausible one.

This repository has the thing none of them have: a cycle-accurate emulator that can run the
cartridge and watch what it does. So this is not a transcription. It is a set of **claims**,
each carrying the evidence that supports it, checked on every build by
[`testharness/gen1atlas.rs`](../../../testharness/gen1atlas.rs) — and the entries with no
evidence say so rather than borrowing confidence from the ones beside them.

That is the same discipline as [`docs/measured/`](../../measured/README.md), applied to a game
instead of to the console.

---

## Coverage

Every byte of work RAM and high RAM is accounted for: named by a symbol, inside a section no
label reaches, or declared unallocated by the linker. There are no holes, because a hole is a
byte nobody has looked at.

| region | span | bytes | named by a symbol | reached by no label | unallocated |
|---|---|---:|---:|---:|---:|
| Video RAM | `$8000-$9FFF` | 8,192 | 8,192 | 0 | 0 |
| Cartridge RAM bank 0 | `$A000-$BFFF` | 8,192 | 6,232 | 0 | 1,960 |
| Cartridge RAM bank 1 | `$A000-$BFFF` | 8,192 | 3,980 | 1,432 | 2,780 |
| Cartridge RAM bank 2 | `$A000-$BFFF` | 8,192 | 6,739 | 0 | 1,453 |
| Cartridge RAM bank 3 | `$A000-$BFFF` | 8,192 | 6,739 | 0 | 1,453 |
| Work RAM | `$C000-$DFFF` | 8,192 | 7,908 | 255 | 29 |
| High RAM | `$FF80-$FFFE` | 127 | 127 | 0 | 0 |

<!-- atlas:end (coverage) -->

Cartridge RAM's four banks are sparse on purpose — bank 0 is a scratch buffer, bank 1 is the
save, banks 2 and 3 are the stored Pokémon boxes — and the unallocated remainder of each is
real spare room on the cartridge, not a gap in this page.

## How an entry was checked

Every row carries an evidence badge. Three things can be true of an address, and they are not
interchangeable:

<!-- atlas:begin (evidence) — generated by tools/gen1-atlas/render.py from atlas.tsv; edit the data, not the table -->

| evidence | entries | what it means |
|---|---:|---|
| **R** — the cartridge names it | 1,594 | the address appears as the operand of an instruction in the ROM image |
| **L** — observed live | 2,694 | the byte changed while the cartridge ran a fixed script on this emulator |
| **I** — an invariant covers it | 36 | a named check proved it means what the atlas says it means |
| *(none)* | 7 | no evidence yet — stated, not hidden |

Storage entries in total: **2,842**.

Written descriptions cover **370 of the 1,012 distinct addresses** (36%). The rest carry their symbol name and their evidence and nothing more, which is the honest state of them — every chapter page reports its own figure at the top of its table.

<!-- atlas:end (evidence) -->

**R — the cartridge names it.** The address appears in the ROM image as the operand of an
instruction that takes one. This is a byte scan, not a disassembly: two bytes of graphics data
preceded by a byte that happens to be `$EA` look exactly like `ld [nn],a`, so a single hit is
weak. What it cannot do is produce a false *negative* — an address the game really does load
will be found.

**L — observed live.** The byte changed while the cartridge ran a **fixed** button script on
this emulator, from a cold boot with no save. Emulation is deterministic, so the same cartridge
and the same script give the same answer for anyone; that is what makes it a baseline and not
an anecdote. The script plays the opening and then walks and opens menus, so it does not reach
a battle or a PC — the entries it never touches are honestly unmarked rather than assumed.

**I — an invariant covers it.** A named, hand-written check proved the entry means what it
says, not merely that it exists. These are the strongest rows in the file and the only kind
that can catch an address which is real, live, and describing the wrong thing:

| invariant | what it establishes |
|---|---|
| party arrays agree | `wPartyCount`, the flat species list and the species inside each 44-byte structure are three statements of one fact, written at different moments. All three agreeing is a claim about all three addresses. |
| party / box strides | `wPartyMon2 − wPartyMon1 = 44` and `wBoxMon2 − wBoxMon1 = 33`, taken from the atlas's own addresses. |
| battle struct is 29 bytes | Two files in this repository disagreed — 28 in one, 29 in another. The map settles it, and `wTrainerClass` following immediately is the proof. |
| money is valid BCD | Every nybble of `wPlayerMoney` is 0-9. A wrong address would almost certainly not be. |
| owned ⊆ seen | You cannot own a Pokémon you have never seen, so every bit of `wPokedexOwned` must be set in `wPokedexSeen`. **Honest limitation, measured not assumed**: the relation is symmetric when the two sets are equal, so on a save where everything seen was caught this check cannot tell the two arrays apart — swapping the symbols survives it. The check says so when that is the case, rather than reporting a pass it has not earned. |
| the party is in the Pokédex | The asymmetric version, and the strongest check here: every species you carry, converted from its **internal index** through `PokedexOrder` *read out of the cartridge*, must have its bit set in `wPokedexOwned`. Three independently located things have to agree. Shifting `PokedexOrder` by one byte breaks it, and breaks the content check beside it — measured. |
| the bag / PC lists are terminated | The count, the pairs and the `$FF` terminator must agree. |
| the live box agrees with itself | `wBoxCount`, `wBoxSpecies` and the species inside each `box_struct`, plus `wCurrentBoxNum` selecting a box that exists. |
| the player has a name | `wPlayerName` and `wRivalName` decode cleanly through the Gen 1 character map — much stronger than "the byte is not zero". |
| the map header is loaded | Width and height are in 32×32 **blocks** and the coordinates are in 16×16 **tiles**; the player must be inside the map when the factor of two is applied correctly. |
| the screen reads back as text | `wTileMap` decodes to a plausible number of letters and spaces mid-play — the property half this project is built on. |
| the warp table is well formed | Every warp's coordinates are on the map whose header is loaded, which ties the table to `wCurMapHeight`/`wCurMapWidth`. |
| the RNG seed moves | Both `hRandomAdd` and `hRandomSub` change within a second of ordinary play. |
| the ROM tables are what they claim | `MonsterNames` really does start at RHYDON, `BaseStats` at Bulbasaur's 45/49/49/45/65, `PokedexOrder` at its eight known dex numbers — read straight out of the cartridge. |

**Teeth, proved rather than claimed.** Moving `wPartyCount` by one byte reddens the ordering
and alias checks; adding a plugin constant the atlas has never heard of reddens the drift gate
by name; shifting `PokedexOrder` by one byte reddens both the content check and the party
cross-reference, independently. And the harness caught one of my own errors while it was being
written: the RHYDON signature had `D` as `$84` instead of `$83`.

It is worth being equally clear about what the tiers **cannot** do. The operand scan cannot
tell code from data. The live sweep only marks what its one script happened to touch, so an
unmarked entry means "not observed", never "not used". And an invariant is only as strong as
the save it runs against — the vacuous `owned ⊆ seen` above is the worked example, and it is
recorded here because a check that quietly passes for the wrong reason is worse than no check.

## Where it comes from, and what is ours

The addresses, the symbol names and the structure layouts are **facts about the cartridge**.
They are derived from a [`pret/pokered`](https://github.com/pret/pokered) checkout built at
RGBDS 1.0.3, whose `pokeblue.gbc` matches that project's own `roms.sha1` — and which is
byte-identical to the retail cartridge this was verified against.
[`tools/gen1-atlas/extract.py`](../../../tools/gen1-atlas/extract.py) re-checks that SHA-1
before it will believe a single address.

**pokered's prose and comments are not ours to copy.** Every description on these pages is
written from scratch, and where a description asserts behaviour rather than restating a name,
either an invariant covers it or it is hedged. Nothing from pokered is vendored here and
nothing is fetched at run time: you point the extractor at your own checkout, or you do not run
it. No ROM is distributed and none of the game's data — no sprites, no text, no tables —
appears in this repository.

## Red, and Yellow

**Red is the same engine and the same layout.** The disassembly builds both from one source and
the work RAM map is shared, so every address here is Red's too; `extract.py --game red` derives
the atlas from Red's own build and can be diffed against this one. The differences are in ROM
data (which Pokémon appear where, a handful of tables) and not in where anything lives.

**Yellow is out of scope and is not approximated.** Its work RAM shifted, so an address from
this page is *wrong* there rather than approximately right — the failure mode being a write
that lands in the middle of somebody else's data and passes its own checksum. Yellow needs its
own build, its own extraction and its own verification run; the machinery here would do it, and
nobody has.

**[Generation 2 has its own area](../../gen2/README.md)** and is deliberately much narrower.

## Working with it

`docs/gen1/atlas/atlas.tsv` is the single source of truth — one row per symbol, nine columns,
tab separated, and it is the exhaustive list. Every table on every page here is generated from
it, so a number in the prose cannot drift away from the map it describes.

```text
# the whole map, greppable
grep -P '\twPartyMon' docs/gen1/atlas/atlas.tsv

# regenerate the derived columns from a built pokered checkout
tools/gen1-atlas/extract.py --pokered ~/src/pokered --write

# regenerate every page from the data
make gen1-atlas

# check the map against a running cartridge
POKE_ROM=~/roms/blue.gb cargo test --release --test gen1atlas
```

Without a cartridge the harness runs its structural tier, says what it skipped, and exits 0 —
so it runs in CI on every build. That tier includes the gate that matters most day to day:
**every Gen 1 address hard-coded in the source must appear in the atlas.** Before this existed,
`wCurMap` was written out in nine separate files and nothing could tell you whether they
agreed. The gate covers 107 constants across nine files today, and a new consumer joins by
being named in `PLUGIN_SOURCES`.

## What this suggests next

* **The scratch chapter is 357 entries of union.** `$CBFC-$D162` is bytes that a dozen
  unrelated routines take turns owning — the slot machine, the Hall of Fame, the trade menus,
  the credits. Reading one without knowing which routine is live is how a tool invents data.
  Naming the *owners* of each union, rather than the members, would be a page of its own.
* **The live sweep never reaches a battle or a PC.** A second script that starts from a save,
  fights something and opens the storage system would move a few hundred entries from "no
  evidence" to observed. The machinery is there; only the script is missing.
* **Sprite compression is named here and not explained.** The decompressor's working state is
  documented in [graphics](graphics.md); the format itself — a bit stream, two planes, an
  optional XOR — deserves the treatment [the sprite decoder](../../trainer.md) already gives it
  in code.
* **A disassembler would upgrade every R badge.** The operand scan is deliberately a heuristic.
  Nothing in this repository can decode an instruction stream yet; `docs/debugging.md` has
  wanted one for other reasons for a long time.
