# Where the three dots are NOT: mode 3, the mode cycle, and `LY`

Measured 2026-08-27 on `0571fb2`. **No emulator change is landed** — `src/` is
byte-identical to the branch point and both engines cost what they did before. This round
went after the offset the previous one named, and the answer is a **second honest
negative**: every placement of those dots is rejected by a hardware measurement of the
quantity it moves. It also **corrects a claim** the previous page made.

## 0. The correction: there is no parity split, and the instrument was at fault

[`sprite-mode3-calibration-2026-08-26.md`](sprite-mode3-calibration-2026-08-26.md) §3/§5
reported the stems splitting into groups needing `+2` and `+4` "exactly by the parity of the
OBJ penalty", and concluded the true offset was a constant three dots that no integer shift
could express. **The split was an artefact of the probe.** It searched for the mode 3 → 0
boundary from the moment OBJ became enabled, which on some ROMs found it on an *earlier*
line than the one the ROM measures. Locking the probe to the line the ROM's own read happens
on collapses the histogram to a single value.

The wider lesson is the one that matters: **that probe should never have been the
instrument.** Its `boundary` is sampled at CPU instruction boundaries, and the ISR's
instructions are not uniform (`ldff a,(c)` is 2 M-cycles, `and` 1, `jp` 4) — so after the
read the sample grid is irregular and the reported boundary quantises unpredictably. The
right instrument was in front of me the whole time: **the ROM's own verdict.** Each pair
resolves the boundary to one M-cycle by construction, and counting pairs where *both*
variants pass needs no probe at all.

```
                         pairs   BOTH PASS   v1-only   v2-only
baseline                   113           0         8       105
```

## 1. The measurement, done properly: a sharp optimum at three dots

Extending mode 3 by a few dots once per line, on any line where an object was fetched
(`src/gpu/fifo.rs`, identical engine only), against all 113 pairs:

| mode-3 tail | BOTH PASS | v1-only | v2-only | Gambatte total |
|---:|---:|---:|---:|---:|
| 0 (shipping) | 0 | 8 | 105 | 3622 |
| 2 | 33 | 8 | 72 | 3702 |
| **3** | **104** | **8** | **1** | **3798** |
| 4 | 71 | 41 | 1 | 3760 |

**Three dots takes 104 of 113 pairs from failing to passing and makes not one pair worse** —
the `v1-only` column is unmoved at 8, and no pair ends in the `neither` column at any tail
length. That is the asymmetry a real fix is supposed to show, and Mealybug is untouched
(29 pixel-exact rows, unchanged) while Gambatte gains 184 rows against 8 lost, six of which
are the sibling variants of pairs that gained.

## 2. And it is still wrong, for a reason stronger than "it trades rows"

Mooneye's `acceptance/ppu/intr_2_mode0_timing_sprites` **measures mode 3's length with
sprites directly**, and our formula already matches it on all 39 arrangements:

| arrangement | mooneye expects | `6 + max(0, 5 − ((X + SCX) mod 8))` per object |
|---|---:|---:|
| 1 sprite at X=8 | 2 M-cycles | 6 + 5 = 11 dots ✓ |
| 10 sprites at X=0 (one tile) | 16 | 60 + 5 = 65 ✓ |
| 10 sprites 8 apart from X0=0 (ten tiles) | 27 | 60 + 50 = 110 ✓ |
| 5 at X=0 + 5 at X=160 (two tiles) | 17 | 60 + 5 + 5 = 70 ✓ |

Reading `intr_2_mode0_timing_sprites.s` rather than trusting the ROM: each case is a
straddle — `41 + N` nops must already be in mode 0 and `40 + N` must not — so it resolves
the length to one M-cycle. **Adding three dots makes the one-sprite case 14 where hardware
says 11.** The tail does not merely cost a row; it contradicts a direct hardware measurement
of the exact quantity it changes. That is disqualifying however well it fits elsewhere.

**A threshold can move which Mooneye row fails, and that is the trap, not the fix.** Arming
the tail only for a sprite with at least one on-screen pixel (`X >= 8`) moves the failure
from `TEST #00` (one sprite at X=0, entirely off-screen) to `TEST #11` (ten sprites at
X=2). Tuning it further is fitting a constant to a suite, which is what this repository's
own rules forbid.

## 3. The whole-cycle lag is rejected harder, by both control suites

If Mooneye pins `mode-2 start → mode-0 start` and Gambatte pins `LY → mode-0 start`, then
together they pin `LY → mode-2 start` — so the whole mode cycle should sit a few dots behind
`LY`. Implemented properly this time, with mode 2, mode 3, the fetcher **and** the mode-2
STAT strobe all moved together:

| | Gambatte | Mooneye | Mealybug |
|---|---:|---:|---:|
| baseline | 3622 | 103 | 29 |
| whole-cycle lag 2 | 3533 | 98 | 11 |
| whole-cycle lag 3 | 3671 | 98 | 11 |

Both controls reject it outright. **A bug worth recording from the first attempt:** the
strobe window is `modeclock >= LINE_DOTS - OAM_STROBE_LEAD`, and shifting mode 2 by `LAG`
tempts you to write `>= LINE_DOTS - (LEAD - LAG)`, which **narrows** the window from four
dots to two rather than moving it. The window has to keep its width and straddle the line
boundary: `modeclock + LEAD >= LINE_DOTS + LAG` for the previous line's tail, plus
`modeclock < LAG` for this line's head. Correcting that changed the numbers and changed
nothing about the verdict.

**Why it cannot work, stated once:** Mealybug arms on the mode-2 **interrupt**, and the CPU
only acts on an interrupt at an M-cycle boundary. Move the PPU three dots and the fetcher
moves exactly three while the ISR that writes into it moves zero or four. The two no longer
line up, and Mealybug's hardware photographs are the referee.

## 4. What the three anchors say, and what is actually left

Three hardware-verified suites, three anchors, and they cannot all be satisfied by moving a
constant:

- **Mooneye** — anchored on **mode 2**, measures mode 3's *length*. Says our length is right.
- **Gambatte** — anchored on the **LYC interrupt**, measures mode 0's *position*. Says our
  mode 0 is three dots early.
- **Mealybug** — anchored on the **mode-2 interrupt**, measures the *fetcher's* position.
  Says our fetcher is right where it is.

Any two of those can be satisfied at once; all three cannot, by any of the placements tried
across this round and the last (mode-3 tail, whole-cycle lag, `LY` lead, LYC-interrupt lead,
per-object penalty). **So one of the three anchors is being modelled wrongly, and the next
step is to find which — not to move another constant.** The sharpest lead is the one thing
common to the two that reject every fix: both Mooneye and Mealybug reach their anchor
through an **interrupt**, where the CPU's M-cycle sampling quantises any sub-M-cycle
placement, while Gambatte's measurement lands on a direct register read that does not. A
model of that sampling — not of the PPU — is where the three dots most likely live.

## 5. Cost

`src/` is byte-identical to `0571fb2`, so nothing moved. Measured on the clean tree with the
repository's own gate (`cargo test --release --test ppuengines`, dmg-acid2):

```
cost  fast 0.0561 ms/frame (298.4x realtime)   accurate 0.4646 ms/frame (36.0x realtime)
```

Every experiment above lived in `src/gpu/fifo.rs` (and, for the strobe, the
`RenderMode::Accurate`-gated arms of `src/gpu/mod.rs`), so none of them could have reached
the `standard` engine or added per-frame work to the shared path. Had one landed, that is
where it would have stayed.

## 6. GBSelfTest

Still not checkable, and now for a sharper reason than last time. The disagreement is
between three *anchors*, and a cartridge can only reproduce anchors the existing suites
already implement — Gambatte's 226 ROMs, Mooneye's 39 arrangements and Mealybug's
photographs between them already measure every one of them, from hardware. A GBSelfTest
check here would be a fourth reimplementation carrying an expectation this work could not
settle. `GB-PPU-16` remains correctly red and is unrelated.

## Reproducing

```
# the pair scorer — the instrument that matters; needs no probe
GB_PPU=accurate ./target/release/examples/csp_suite --suite gambatte \
    --dir target/test-suites/csp > run.txt
# count pairs in sprites/space where both variants pass

# Mooneye's own table, which is the control that rejects the tail
git clone --depth 1 https://github.com/Gekkio/mooneye-test-suite
sed -n '70,200p' mooneye-test-suite/acceptance/ppu/intr_2_mode0_timing_sprites.s
```
